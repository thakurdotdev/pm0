This guide walks through the everyday pm0 workflow. It assumes pm0 is
[installed](/docs/installation) and on your `PATH`.

## Start your first app

Any Node entrypoint works out of the box. The `-i max` flag starts one cluster
worker per CPU core, all sharing one port (Node.js and Bun):

```bash
pm0 start api.js          # single fork process
pm0 start api.js -i max   # cluster mode
```

<Callout type="info" title="npm start, pnpm, bun run…?">
  To run a `package.json` script instead of a file, the program is the
  package manager and the script goes after `--`:
  `pm0 start npm --name api -- start`. When to choose which (and what it
  costs) is covered in [Starting Your App](/docs/starting-apps).
</Callout>

## Runtimes

pm0 picks the runtime from a shebang line first, then from the file
extension (`.js/.mjs/.cjs` → node, `.py` → python3, `.sh` → sh, `.rb`,
`.php`, `.pl`). TypeScript has no single default runtime, so name one:

```bash
pm0 start app.js                         # Node.js (auto)
pm0 start app.ts --interpreter bun       # Bun
pm0 start app.ts --interpreter node      # Node ≥ 22.18 (native type stripping)
pm0 start app.ts --interpreter deno      # Deno
pm0 start main.py                        # Python (auto)
pm0 start worker.sh                      # shell script (auto)
pm0 start ./server                       # prebuilt Go/Rust binary (build it first)
```

`pm0 start app.ts` without an interpreter (and without a shebang) is refused
with a hint. Go sources are not compiled for you: run `go build` and start
the binary.

For a prebuilt binary where pm0 should not prepend any interpreter:

```bash
pm0 start ./dist/server --interpreter none
```

<Callout type="info" title="Cluster mode: Node.js and Bun">
  `-i max` / `-i N` uses SO_REUSEPORT for kernel-level zero-downtime reloads.
  That requires **Node ≥ 23.2** or **Bun**, and **kernel ≥ 3.9**. Other
  runtimes (and apps started through npm/pnpm/yarn) run as fork families with
  no shared port. See [Core Concepts](/docs/core-concepts).
</Callout>

## Manage the app

```bash
pm0 status                # table of processes
pm0 describe api          # full details for one process
pm0 logs api              # stream logs
pm0 logs api --err        # stderr only
pm0 scale api 4           # grow/shrink a cluster to 4 workers
pm0 reload api            # zero-downtime rolling reload (sequential)
pm0 restart api           # full restart
pm0 stop api              # stop (SIGINT → kill_timeout → SIGKILL)
pm0 delete api            # stop and remove from the list
```

## Persist across restarts

Save the current process list, enable boot persistence, and restore:

```bash
pm0 save                  # snapshot $PM0_HOME/dump.pm0
pm0 startup               # print the systemd/boot integration command
pm0 resurrect             # restore the saved list
```

The full sequence for a server is described in the
[systemd guide](/docs/guides/systemd).

## Ecosystem files

Use your existing PM2 ecosystem file directly:

```bash
pm0 start ecosystem.config.js
pm0 start ecosystem.config.js --only api
pm0 start ecosystem.config.js --env production
```

See [Ecosystem File](/docs/ecosystem-file) for the supported fields and env
layering rules.
